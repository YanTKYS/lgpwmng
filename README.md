# lgpwmng

自治体業務システム向けのログイン情報入力補助を行う Chrome 拡張（Manifest V3）です。

汎用パスワードマネージャの再実装ではなく、**自治体業務システムに多い「複数項目・複数アカウントのログイン画面」へ、安全かつ素早く認証情報を入力する**ことに特化しています。

- 外部 API・クラウド・CDN を一切利用しません（閉域環境で動作します）
- 認証情報は Web Crypto API（PBKDF2 + AES-GCM）で暗号化して端末内にのみ保存します
- ログインボタンの自動押下は行いません。最終的なログイン操作は利用者が行います

バージョン: **v0.4.1**

---

## 1. lgpwmng とは

自治体の業務システムでは、次のようなログイン画面が珍しくありません。

- ID / パスワード以外に、自治体コード・団体コード・所属コード・職員番号・第二パスワード・PIN などの入力欄がある
- 同一ドメイン配下でも、パス違いで別システムのログイン画面になっている
- 1 つのシステムに「通常業務用」「管理者用」など複数のアカウントを使い分ける必要がある

Chrome 標準のパスワード管理はこうした画面を想定していないため、
「入力欄の一部しか自動入力されない」「アカウントを取り違える」といった問題が起こります。

lgpwmng は、**サービス単位で任意の入力項目を定義**し、
**登録済みの値をまとめて入力する**ことでこれを補完します。

## 2. 想定利用環境

| 項目 | 内容 |
| --- | --- |
| ブラウザ | Google Chrome / Chromium 116 以上（Manifest V3） |
| OS | Windows / macOS / Linux（拡張が動作する環境） |
| ネットワーク | 閉域（LGWAN 等）で利用可能。拡張は外部通信を行いません |
| 配布方法 | Chrome ウェブストアを経由しない、組織内での手動配布 |
| 権限 | `activeTab` / `scripting` / `storage` のみ |

`<all_urls>` などの広範な恒久権限は要求しません。ページへのアクセスは、
**利用者が拡張アイコンを操作したタイミング**に限られます（常駐 content script はありません）。

## 3. インストール方法

1. 本リポジトリの内容を、端末内の任意のフォルダへ配置します（例: `C:\tools\lgpwmng`）。
2. Chrome で `chrome://extensions` を開きます。
3. 右上の **デベロッパーモード** を有効にします。
4. **パッケージ化されていない拡張機能を読み込む** をクリックし、`manifest.json` があるフォルダを選択します。
5. ツールバーに lgpwmng のアイコンが表示されれば読み込み完了です（必要に応じてピン留めしてください）。

> 組織内展開時は、フォルダごと配布するか、`chrome://extensions` の「拡張機能をパッケージ化」で
> `.crx` を作成して配布してください。Chrome ウェブストアへの公開は前提としていません。

## 4. 基本的な使い方

### 4.1 マスターパスワードの設定（初回のみ）

1. 拡張アイコンをクリックします。
2. マスターパスワード（8 文字以上）を 2 回入力し、「設定する」を押します。

登録した認証情報はこのパスワードから導出した鍵で暗号化されます。
**マスターパスワードは保存されないため、忘れると復元できません。**

### 4.2 ログイン情報の入力

1. 対象のログイン画面を開いた状態で、拡張アイコンをクリックします。
2. 現在の URL に対応するサービスが判定され、アカウント一覧が表示されます。
3. アカウントを選び、「ログイン情報を入力」を押します。
4. 登録済みの項目に値が入力されます。**ログインボタンは押されません**ので、内容を確認のうえ利用者自身がログイン操作を行ってください。

入力の直前に、現在のタブの URL が選択中のサービスの登録条件に一致するかを再確認します。
popup を開いた後にページが遷移した場合など、条件に一致しなくなっていれば **1 項目も入力しません**。

入力結果は項目ごとに表示されます。次の場合は警告として表示されるので、値を確認してください。

| 表示 | 意味 |
| --- | --- |
| 入力しました | 入力欄を確実に特定できた |
| 入力しました（候補一致が弱いため要確認） | 通常項目で、入力欄の特定が確実ではない |
| 入力欄を特定できないため入力していません | **秘密項目**で特定が確実ではないため入力を見送った。「このログイン画面の設定を編集」から対応付けを更新してください |
| 入力先のフレームを特定できないため入力していません | 対象のフレームを一つに絞り込めなかった（詳細は 5.4） |
| 入力欄が見つかりません | 該当する入力欄がページ上に無い |
| 入力に失敗しました | 入力欄に値を反映できなかった。選択肢（`select`）に無い値や、ラジオボタンの値が登録値と一致しない場合など |

## 5. サービス登録方法

### 5.1 ログイン画面から登録する（推奨）

1. 業務システムのログイン画面で、ユーザーID・パスワードなどをいつもどおり入力します。
2. 拡張アイコン →「このログイン画面を設定」をクリックします。
3. 設定ページが開き、ページ上の `input` / `select` / `textarea` が候補として一覧表示されます。
   - `id` / `name` / `type` / `autocomplete` / ラベル / プレースホルダから項目名を推定します。
   - **推定結果は初期値です。** 必ず内容を確認して確定してください。
   - 「確認」ボタンで、対象のログイン画面上の該当入力欄を強調表示できます。
   - **新規登録の場合、手順 1 でログイン画面に入力済みだった値がそのまま「標準ユーザー」アカウントの
     初期値として反映されます。** ログイン画面と設定ページの両方へ同じ値を入力し直す必要はありません
     （詳細は 5.5）。
4. 各項目について以下を設定します。

   | 設定 | 内容 |
   | --- | --- |
   | 使用 | その項目を入力対象にするか |
   | 表示名 | 自治体コード / 職員番号 / 第二パスワード など任意の名称 |
   | 区分 | **共通**（サービス共通値）か **アカウント**（アカウントごとの値）か |
   | 種別 | 通常 / 秘密（秘密は画面上マスク表示されます） |
   | 対象入力欄 | ページ上のどの入力欄に入力するか |

5. サービス名・URL 条件（オリジン / パス）を確認します。
6. 画面下部の「アカウント」でアカウントを設定します。標準で 1 件用意されていますが、
   「＋ アカウントを追加」でその場のまま 2 件目以降も追加でき、通常 / 管理者の区分や
   ユーザーID・パスワードなどの値もこの画面だけで入力できます。不要なアカウントは削除できます。
7. 共通値・アカウントの値を入力し、「保存」を押します。

項目は自由に追加・削除できます。ID とパスワードの 2 項目に限定されません。
新しい項目を増やすためにソースコードを変更する必要はありません。

保存後もこの画面から続けてアカウントを追加・編集できます。「サービス一覧」（options.html）へ
移動する必要はありません。既存サービスのログイン画面を開いて設定を編集する場合も同様です。

### 5.2 URL 条件について

サービスの判定は **オリジン + パス** で行います。オリジンはプロトコル・ホスト名・ポートを含みます。

```text
https://sample-service.sample-company.asp.lgwan.jp/login
└───────────────── origin ──────────────────────┘└ path ┘
   protocol + hostname (+ port)
```

| 判定 | 意味 |
| --- | --- |
| オリジン：完全一致 | プロトコル・ホスト名・ポートがすべて一致する場合のみ |
| オリジン：サブドメイン含む | `https://asp.lgwan.jp` を指定すると `https://xxx.asp.lgwan.jp` も一致（プロトコルとポートは一致が必要） |
| パス：完全一致 | `/login` のみ一致 |
| パス：前方一致 | `/apply` を指定すると `/apply/login` も一致 |
| パス：パス問わず | オリジンだけで判定 |

**`http` と `https` は別のものとして扱います。** `https://example.lgwan.jp/login` として登録した認証情報が
`http://example.lgwan.jp/login` へ入力されることはありません。ポート番号の違いも別サービスとして扱います。

`http` の業務システムにもそのまま対応します。プロトコルを利用者が選択する必要はありません。

- **新規登録**: 現在開いているページの `URL.origin`（プロトコル + ホスト名 + ポート）をそのまま自動取得します。
  `http://service.asp.lgwan.jp:8080/login` を開いていれば `http://service.asp.lgwan.jp:8080` として登録されます。
- **v0.1.0 で登録した条件の移行**: v0.1.0 のデータにはプロトコルの記録がありません。
  lgpwmng が `http` / `https` を推測することはなく、**対象のログイン画面を実際に開いて拡張アイコンを押した時点**で、
  そのページのオリジンを採用して自動的に新形式へ移行し、暗号化 Vault へ保存します（次回以降は通常の条件として扱われます）。
  移行が済むまでの条件はどの URL にも一致しないため、プロトコル不明のまま認証情報が入力されることはありません。
  対象ページを開くまでは旧条件がそのまま保持され、登録済みの認証情報が失われることもありません。
  設定ページの「対象URL」欄には、移行前の条件がプレースホルダとして表示されます（手入力での確定も可能です）。

なお、設定ページのオリジン欄に利用者がプロトコルを省略して入力した場合のみ、`https` を補って保存します
（保存済みデータのプロトコルを推測することはありません）。

パス欄は、先頭の `/` を省略して入力しても補われます（`login` → `/login`）。
末尾の `/` の有無は判定に影響せず、誤って付けたクエリ（`?` 以降）は取り除かれます。
整えた結果は入力欄にそのまま表示されるので、保存前に確認できます。

同一ドメイン配下でもパスが異なる場合は、別サービスとして登録できます。
複数のサービスが一致した場合は、より厳密な条件のサービスが優先され、popup 上で切り替えられます。

### 5.3 設定ページからの編集

拡張アイコン →「サービス一覧」（または `chrome://extensions` の「拡張機能のオプション」）から、
サービス名・URL 条件・入力項目・共通値・アカウントをまとめて編集できます。

サービス選択直後はアカウント（追加・削除・ID/パスワード変更・通常/管理者区分）が主要な領域として
表示されます。対象URL・入力項目・サービス共通値は「▶ サービス設定」の折り畳みの中にまとまっており、
初回設定時以外はあまり操作しない項目のため初期状態では閉じています。

### 5.4 フレーム内のログイン画面（frame / iframe）

`frameset`／`frame` を使った古い業務システムや、`iframe` でログインフォームを埋め込んだ画面にも対応しています。

- 「このログイン画面を設定」を実行すると、トップページだけでなく、アクセス可能な `frame` / `iframe`
  すべてを走査し、候補として一覧表示します。`<frame>` と `<iframe>` は区別せず同じ扱いです。
- 同じ推定名（例: ユーザーID）の入力欄が**異なるフレームに複数存在する**場合、自動では確定しません。
  候補には `[フレーム: ○○]` のように補足が付くので、内容を確認してから使用する項目を選んでください。
- 登録した項目には、対象がどのフレームかという情報（フレームの origin・パス・フレーム名）が保存されます。
  Chrome のフレーム番号（frameId）はタブを開き直すたびに変わり得るため保存には使わず、入力の都度、
  現在のフレーム構成から対象フレームを再特定します。
- 対象フレームを一つに絞り込めない場合（フレームが見つからない、または同程度に一致するフレームが複数ある場合）、
  **秘密項目（パスワード等）は安全のため入力しません。** 通常項目のみ、参考として弱い一致で入力を試みます。
- 別オリジンのフレームは、Chrome の権限上アクセスできないことがあります。その場合は無理に回避せず、
  エラーとして表示します。

### 5.5 入力済みの値の取り込み

新しいサービスを登録するとき、ログイン画面に既に入力されている値を、設定ページで
もう一度入力し直す必要がないようにする機能です。

- **対象は新規登録のときだけです。** 既存サービスの設定を編集する場合（「このログイン画面の設定を編集」）は、
  値の取り込みは行いません。登録済みの認証情報が、ページ上の値で無確認に置き換わることはありません。
- 取り込みは、「このログイン画面を設定」を実行した時点で 1 回だけ行われます。
  常時ページを監視したり、入力のたびに値を収集したりはしません。
- 取得できるのは、走査（候補一覧の作成）で対象になった `input` / `select` / `textarea` の現在の値です。
  空欄の入力欄は取り込みません。
- 入力欄の判定は候補との対応付け（`id` → `name` → CSS セレクタ）で行うため、複数の入力欄がある画面でも
  値が入れ替わって取り込まれることはありません。フレーム内（5.4）の入力欄にも対応しています。
- 取得した値は、初期作成される「標準ユーザー」アカウントの初期値として設定ページ上（メモリ上）に
  反映されるだけで、保存を押すまで暗号化 Vault へは書き込まれません。設定ページを閉じたり読み込み直したり
  すると消え、復元もされません（取得し直したい場合は、ログイン画面から改めて設定を開始してください）。
- 秘密項目（パスワード等）は、通常のアカウント編集と同様「••••••••」で表示され、「表示」を押した場合のみ
  内容を確認できます。
- 「対象入力欄」の選択を変更した場合、取り込んだ値も新しく選んだ入力欄の現在値へ差し替わります
  （元の入力欄の値を引き継ぎません）。ただし、設定ページ上で値を手入力で修正した後は、
  その内容を上書きしません。
- 「再スキャン」は候補一覧（入力欄の構造）だけを更新し、値を取得し直すことはありません。
- 値を取得できなかった場合（対象ページへアクセスできない等）でも、候補の走査に成功していれば
  登録自体は通常どおり行えます。値は手入力してください。

## 6. サービス共通値とアカウント

### 6.1 サービス共通値

アカウントごとに重複登録する必要のない値は「共通」区分にします。

```text
自治体コード：123456   ← サービス共通値
```

### 6.2 複数アカウント

1 つのサービスに複数のアカウントを登録できます。名称は自由に付けられます。

```text
○○申請システム
  ├─ 標準ユーザー（通常）    ユーザーID / パスワード / 第二パスワード
  └─ 管理ユーザー（管理者）  ユーザーID / パスワード / 第二パスワード
```

### 6.3 アカウントの切り替えと管理者アカウント

popup 上のアカウント一覧から選択して切り替えます。
管理者区分のアカウントには次の安全策があります。

- **既定では選択されません**（既定選択は通常区分のアカウントのみ）
- 選択すると「管理者アカウントを使用します」のチェックが必要になり、チェックするまで入力できません
- popup と設定ページで「管理者」バッジ・警告色を表示します
- 自動的に選択して即入力する動作は行いません

## 7. マスターパスワード

- Vault（登録データ全体）はマスターパスワードから導出した鍵で暗号化されます。
- マスターパスワード自体は保存されません。ハッシュも保存しません。
  復号に成功するかどうかで正否を判定します（AES-GCM の認証タグ）。
- Chrome を再起動すると必ずロック状態に戻り、再度入力が必要です。
- popup / 設定ページの「ロック」でいつでも明示的にロックできます。
- 変更は「サービス一覧」→「マスターパスワード / バックアップ」タブから行えます。

## 8. バックアップ・復元

設定ページの「マスターパスワード / バックアップ」タブから操作します。

- **エクスポート**: バックアップ用パスフレーズ（8 文字以上）を入力すると、
  暗号化された JSON ファイル（`lgpwmng-backup-YYYYMMDDhhmmss.json`）が保存されます。
  ファイル内は暗号化されており、認証情報が平文で出力されることはありません。
- **復元**: バックアップファイルとパスフレーズを指定します。
  取り込み方法は「追加（既存サービスを残す）」と「置換（既存サービスを削除）」から選べます。

> バックアップ用パスフレーズはマスターパスワードとは独立に指定できます。
> パスフレーズを忘れたバックアップは復元できません。
> ファイル自体は暗号化されていますが、業務上の取り扱いルールに従って保管してください。

端末間の自動同期は v0.1.x では実装していません。

## 9. セキュリティ上の注意

実装上の方針:

- `chrome.storage.local` には **暗号化済み Vault のみ** を保存します（平文保存はしません）。
- 鍵導出は PBKDF2-SHA256（310,000 回、16 バイトソルト）、暗号化は AES-GCM 256bit。独自暗号は実装していません。
- アンロック中の導出鍵は `chrome.storage.session`（`TRUSTED_CONTEXTS`）にのみ保持し、ブラウザ終了時に破棄されます。
  復号済みの Vault は Service Worker のメモリ上にのみ存在し、永続化しません。
- ページ側（content script 相当の注入コード）へ Vault 全体を渡しません。
  **入力が必要になった項目の値だけ**を、入力実行時に引数として渡します。
- 常駐 content script は登録せず、利用者が拡張を操作したときだけ `chrome.scripting` で注入します。
- **入力直前に URL を二重に確認します。** background で現在のタブ URL を取得して照合し、
  さらに注入したコード自身がページの `location` を再確認します。URL を取得できない場合も入力しません。
- **秘密項目は入力欄の特定が確実な場合のみ入力します。** 識別情報の一致が弱い場合、通常項目は警告付きで
  入力しますが、パスワード等の秘密項目は入力せず、設定の更新を促します。
- 秘密情報を `console` へ出力しません。ページ走査結果に入力欄の値は含めません。

利用上の注意:

- **端末の管理が前提です。** OS アカウントを共有している端末では、ロック状態でも
  暗号化ファイル自体は取得され得ます。共有端末での利用は避けてください。
- マスターパスワードは十分な長さのものを設定し、他システムと使い回さないでください。
- 席を離れる際は「ロック」を実行してください（自動ロック時間の設定は v0.3.0 では未実装です）。
- 拡張のデベロッパーモード読み込みは、フォルダの改変が拡張の挙動に直結します。
  配布フォルダは書き込み権限を制限してください。
- 入力先が意図した入力欄か、入力後に必ず目視で確認してください。

## 10. Chrome 標準パスワードマネージャとの違い

| 観点 | Chrome 標準 | lgpwmng |
| --- | --- | --- |
| 入力項目 | ユーザー名 / パスワードが中心 | 任意の項目を数に制限なく定義（自治体コード・職員番号・第二パスワード等） |
| サービス判定 | 主にオリジン（ドメイン）単位 | オリジン + パスで判定。同一ドメインのパス違いも別サービスにできる |
| 共通値 | 概念なし | サービス共通値として 1 か所で管理 |
| 複数アカウント | 候補一覧から選択 | サービスごとに名称付きで管理し、通常 / 管理者の区分を持つ |
| 管理者アカウント | 区別なし | 既定で未選択・明示的な確認を必須にして誤使用を防止 |
| 入力の起点 | ページ表示時の自動入力が中心 | 利用者が拡張アイコンを押したときのみ入力 |
| ログイン実行 | 自動送信されることがある | **自動送信しない**（送信は利用者操作） |
| 保管 | ブラウザプロファイル / アカウント同期 | 端末内のみ。マスターパスワードで暗号化。外部通信なし |
| 同期 | Google アカウント同期 | なし（暗号化バックアップの手動移行のみ） |

Chrome 標準を置き換えるものではなく、**業務システムのログイン画面に限って補完する**位置づけです。

## 13. 既知の制約

- `frame` / `iframe` 内のログイン画面には対応していますが（詳細は 5.4）、Shadow DOM 内の入力欄には対応していません。
- フレームが**別オリジン**の場合、Chrome の権限モデル上アクセスできないことがあります。その場合は無理に回避せず、
  「一部のフレームを確認できませんでした」等のエラーとして扱います。
- 画面遷移型（ID 入力 → 次画面でパスワード）のログインは、画面ごとにサービスを登録して個別に入力してください。
- 入力欄が JavaScript で動的に生成される画面では、入力欄が表示された状態で「このログイン画面を設定」を実行してください。
- DOM 変更耐性は `id` / `name` / ラベル / セレクタ等の複数ヒントによる照合で確保していますが、
  画面が大きく改修された場合は「このログイン画面の設定を編集」から対応付けを更新してください。
  特に秘密項目は弱い一致では入力されないため、この場合は設定の更新が必要です。
- 同一の業務システムが `http` と `https` の両方で提供されている場合は、URL 条件をそれぞれ登録してください。
- 拡張の権限上、`chrome://` などブラウザ内部ページでは動作しません。
- 入力済みの値の取り込み（5.5）は新規サービスの登録時のみです。既存サービスの設定を編集しても、
  ログイン画面の現在値でアカウントの登録済みの値が自動的に更新されることはありません。
  最新の値へ更新したい場合は、これまでどおり手動で編集してください。
- 取り込んだ値は設定ページを保存するまでの一時的な下書きです。ページを閉じたり読み込み直したりすると
  消え、復元されません（マスターパスワードと同様、平文の認証情報を残さないことを優先しています）。

### v0.4.0 — ログイン画面の入力済み値取り込み

新しいサービスを登録するときの二重入力（ログイン画面への入力 → 設定ページへの再入力）を解消しました。
Vault のデータ形式は変更していません（`schemaVersion` は変更なし。取得した値は、既存の

- **新規サービスの設定を開始すると、ログイン画面に入力済みの値が「標準ユーザー」アカウントの

  - 走査（候補一覧の作成、scan）とは別の処理（capture）として実装し、常駐監視は追加していません。
    値を取得するのは、利用者が「このログイン画面を設定」を実行した直後の 1 回だけです。

  - 取得した値はページを離れる（保存する）までメモリ上の下書きとして扱い、`chrome.storage` 等の
    一時ストレージへ平文で保存することはありません。設定ページを閉じる・読み込み直すと消えます。
  - 設定ページで「対象入力欄」を切り替えた場合は取り込んだ値も追従し、利用者が値を手入力で
    修正した後はその内容を上書きしません。
  - 既存サービスの設定を編集する場合は取得しません（登録済みの値を無確認で置き換えないため）。

### v0.3.3 — 不具合修正と整理

日常の利用で支障となる不具合の修正と、読みやすさのための整理を行いました。
Vault のデータ形式は変更していません（`schemaVersion` は変更なし）。

**不具合修正**

- **チェックボックス / ラジオボタンの項目で、入力時に `input` / `change` を二重に発火していたのを修正しました。**
  クリック操作自体がこれらのイベントを発火するにもかかわらず、続けて同じイベントを送っていたため、
  `onchange` で入力チェックを行う業務システムで検証が二度走っていました（v0.3.1 で修正した `blur` の
  二重発火と同じ原因です）。
- **ラジオボタンの項目で、登録値と一致しないのに「入力しました」と表示していたのを修正しました。**
  ラジオボタンはクリックでは解除できないため実際には何も変わっておらず、区分が切り替わっていないことに
  気付けませんでした。この場合は入力できなかったものとして表示します。
  併せて、状態が変わらない無意味なクリックをページへ送らないようにしました。
- **項目名の自動判定が効かない画面があったのを修正しました。**
  `<label><input></label>` のように文字を持たないラベルが付いていると、そこで手掛かり探しが
  打ち切られ、表のセルや直前の見出しからラベルを拾えていませんでした。中身のある文字列だけを採用します。
  項目名の推定に加えて、入力欄の再特定の精度も上がります。
- **ログイン画面設定ページで、設定を読み込めなかったときに「再スキャン」や「保存」を押すと
  操作が何も起きなくなる不具合を修正しました。** 読み込めていない旨を表示します。
- **「アカウントを追加」の既定名が実際の件数とずれていたのを修正しました。**
  「標準ユーザー」1 件だけのサービスで最初に追加すると「アカウント2」になっていました。
  使われていない最も小さい番号を使います。
- **アカウントの自動保存で、保存していないのに「保存済み」と表示することがあったのを修正しました。**
  保存が実行されるまでに別のサービスへ切り替えた場合、その内容は保存しません。

**整理（動作は変わりません）**

- 「確認」（入力欄の強調表示）が失敗したときの案内を理由ごとの一覧にまとめ、
  フレーム構成を確認できなかった場合に「入力欄が見つかりません」と誤って案内していたのを改めました。
- ページ内処理の呼び出しを `runPageAgent()` 一つにまとめ、全フレーム実行と単一フレーム実行は
  その薄い呼び分け（`runInAllFrames()` / `runInFrame()`）にしました。同じ内容の例外処理が
  3 か所に重複していたのを解消しています。
- 走査できなかったフレームの判定を `hasUnreachableFrames()` として切り出し、`scanPage()` を短くしました。
- 値の反映処理（`applyValue()`）を、入力欄の種類ごとに「値を入れる」「ページへ通知する」が
  1 か所で読み取れる形へ整理しました。

### v0.3.0 — フレーム内ログインフォーム対応

`frameset` / `frame` を使った古い業務システムや `iframe` でログインフォームを埋め込んだ画面に対応しました。
Vault のデータ形式は変更していません（`schemaVersion` は変更なし。既存項目にフレーム情報が無い場合は
自動的にトップフレーム扱いとして読み込まれます）。

- **走査（スキャン）が全フレームを対象になりました。** トップページに加えて、アクセス可能な
  `frame` / `iframe` すべてで入力欄を探し、候補として集約します。`<frame>` と `<iframe>` は区別しません。
- **項目ごとにフレーム情報を保存するようにしました。** 対象入力欄がどのフレーム（origin・パス・フレーム名）に
  属するかを保存し、入力の都度、現在のフレーム構成から対象フレームを再特定します。Chrome のフレーム番号
  （frameId）はタブを開き直すたびに変わり得るため、保存データには使っていません。
- **同じ推定名の入力欄が複数フレームにまたがる場合、自動では確定しません。** setup.html の候補一覧には
  `[フレーム: ○○]` の補足を表示し、利用者が使用する項目を選べるようにしました。
- **フレームを一つに絞り込めない場合、秘密項目は入力しません（fail closed）。** 対象フレームが見つからない、
  または同程度に一致するフレームが複数ある場合、既存の「locator の弱一致では秘密項目を入力しない」方針を
  フレームの特定にも適用しています。通常項目のみ、参考として弱い一致で入力を試みます。
- **入力直前にフレーム自身の URL も再確認するようにしました。** トップページの URL 確認（background 側・
  ページ側の二重確認）はそのまま維持したうえで、子フレームへ入力する場合は、そのフレーム自身の
  URL（origin + パス）も入力の直前に再確認します。query 文字列は比較対象に含めていません。
- 「強調表示」「再スキャン」も全フレーム対応にしました。再スキャンは frameId の一致に頼らず、
  フレーム自身の URL・名前で既存の対応付けをできるだけ保持します。
- 走査したフレームの数が想定より少ない場合（アクセスできなかったフレームがある可能性がある場合）は、
  候補が 0 件のときと区別して「一部のフレームを確認できませんでした」と表示するようにしました。
- background 側のフレーム再特定・入力ロジックは `runPageAgentAllFrames` / `runPageAgentInFrame` として
  整理し、`page-agent.js` 自体の scan / fill / highlight という自己完結した構造は維持しています。

### v0.2.2 — 自動保存とサービス設定の状態分離

v0.2.1 のレビューで、未保存の「サービス設定」（入力項目の区分変更・削除）が
アカウントの自動保存に混ざる可能性があるという指摘を受けて修正しました。
Vault のデータ形式・暗号化方式の変更はありません（`schemaVersion` は変更なし）。

- **未保存の入力項目変更が、アカウントの自動保存に巻き込まれないようにしました。**
  入力項目の区分（共通 / アカウント）を変更したり項目を削除したりすると、画面上は
  即座に値が移動・消去されて見えます（この見た目自体は従来どおりです）。しかし
  これらは「サービス設定」の一部で明示保存が前提のため、保存されるまでの間に
  アカウント名の変更などで自動保存が走っても、影響を受けた値は**直前に保存済みの
  内容のまま**送るようにしました。「サービス設定を保存」（または setup.html の
  「保存」）を押して初めて、区分変更・削除がアカウント値にも反映されます。
- **明示的な「保存」は、クリックした時点の内容で確定してから送るようにしました。**
  保存ボタンを押した処理がアカウントの自動保存の後ろに並んでいる間に、さらに
  URL・入力項目を編集しても、その保存クリックが後から編集した内容まで巻き込んで
  保存することはありません。
- この判定・復元ロジック（`buildSafeAccountsPayload`）と、保存直後のスナップショット
  作成（`snapshotService`）は `src/ui/account-editor.js` に共通化し、setup.html /
  options.html の双方が同じ実装を利用しています。

### v0.2.1 — アカウント変更の自動保存

アカウントの追加・編集は日常的に行う操作のため、保存忘れが起きないようにしました。
Vault のデータ形式・暗号化方式の変更はありません（`schemaVersion` は変更なし）。

- **既に保存済みのサービスでは、アカウントの追加・削除・名前変更・通常/管理者区分の変更・
  各項目値（ID・パスワード・第二パスワード等）の変更を自動保存するようにしました。**
  setup.html・options.html のどちらでも、アカウントを変更したあとに改めて「保存」を押す必要は
  ありません。テキスト入力は打鍵のたびにではなく、確定（`change` / フォーカスが外れたタイミング）
  で保存します。追加・削除・区分変更のように操作が明確に確定するものはその場で保存します。
- **対象URL・入力項目・サービス共通値・サービス名は、従来どおり明示的な「保存」のままです。**
  自動保存はアカウントのみを対象とし、これらの項目を保存するには options.html の
  「サービス設定を保存」（旧「保存」）ボタン、または setup.html の「保存」ボタンを押してください。
  アカウントの自動保存が、保存されていないURL・入力項目の変更を巻き込んで保存することはありません。
- **新規サービスは最初の1回だけ明示保存が必要です。** サービスIDが確定していない新規サービスでは
  アカウントを変更しても自動保存されません。最初の保存が完了した後は、そのままの画面でアカウントを
  追加・編集すると自動保存されます。
- アカウント領域に小さな保存状態表示（「保存中…」「保存済み」）を追加しました。保存に失敗した場合は
  「保存できませんでした」と明確に表示し、`[再試行]` から再送できます。失敗した入力内容が画面から
  消えることはありません。
- 保存処理は直列化されており、短時間に複数の変更が発生しても、古い保存処理が後から完了して
  新しい値を上書きすることはありません。常に最後に確定した内容が Vault へ反映されます。
- 自動保存のトリガーと直列保存キューは `src/ui/account-editor.js` に共通化し、setup.html /
  options.html の双方から同じ実装を利用しています。

### v0.1.4 — 不具合修正と整理

業務中に実際に支障となる不具合を修正しました。データ形式の変更はありません。

- **ログイン画面設定ページで「保存」を 2 回押すと、登録した値がすべて消えていた問題を修正**しました。
  2 回目の保存で入力項目が別物として扱われ、値の対応付けが外れていたためです。
  保存後は項目の対応付けを保持し、続けて保存し直しても値はそのまま残ります。
- **同じ画面で「保存」を続けて押すと、同じサービスが二重に登録されることがあった問題を修正**しました。
  保存中はボタンを押せないようにしています。
- **項目の区分（共通 / アカウント）を変更すると、アカウントごとに登録していた値が失われていた問題を修正**しました。
  変更前の区分の値を消さずに残すため、区分を戻せば各アカウントの値が元のまま使えます。
- **設定ページで「再スキャン」すると、入力中の項目や手動で追加した項目が消えていた問題を修正**しました。
  行は作り直さず「対象入力欄」の選択肢だけを更新します。表示名を書き換えていても値は失われません。
- **入力欄の多いログイン画面で、走査・入力に時間がかかり画面が固まったようになる問題をさらに改善**しました。
  入力欄ごとにページ全体を数え直していた処理をやめています（入力欄 300 件の画面で約 1/4 の時間）。
  入力欄の識別情報は従来と同一で、登録済みの設定はそのまま使えます。
- **ログイン画面設定ページで対象URLの条件を書き換えても保存されなかった問題を修正**しました。
  条件欄を触っていない場合に条件を重複追加しない動作は従来どおりです。
- 走査結果をタブごとに保持し続けていたのをやめ、直前の 1 件だけを保持するようにしました。
  別のタブの走査結果が設定ページへ渡ることもなくなります。

### v0.1.2 — 旧 URL 条件の実 URL ベース自動移行

- v0.1.0 形式（プロトコル情報を持たない `hostname`）の URL 条件を `https` とみなす暗黙変換を廃止しました。
  lgpwmng がプロトコルを推測することはありません。
- プロトコル未確定の条件はそのまま保持し（`schemaVersion` 3）、対象のログイン画面を実際に開いた時点で、
  そのページのオリジンを採用して新形式へ自動移行し、Vault へ保存します。サブドメイン一致の条件も意味を保って移行します。
- 現在のページが旧条件に一致しない場合は、条件を書き換えず、認証情報も入力しません。
  移行後も、入力時には通常どおり URL の再検証を通します。

### v0.1.1 — 認証情報入力時の安全性補強

- 入力の直前に URL を再確認するようにしました。background で現在のタブ URL を取得してサービスの
  条件と照合し、注入したコード自身もページの `location` を再確認します（不一致・URL 不明なら入力しません）。
- URL 判定を `hostname + pathname` から **`origin + pathname`** へ変更しました。
  プロトコルとポートを含めて判定するため、`http` と `https` を区別します。
  旧形式で保存された条件は、読み込み時に `https` のオリジンとして移行されます。
- 秘密項目（種別「秘密」）は、入力欄の特定が確実な場合のみ入力するようにしました。
  一致が弱い場合は入力せず、設定の更新を促します（通常項目は従来どおり警告付きで入力します）。
